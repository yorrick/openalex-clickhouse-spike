## Must fix

**F1 — The cache's effect on time is overstated** (`duckdb-extraction-benchmark.md:21`, RD draft `:17`).
- The byte saving is genuinely caused by the cache: body bytes fell 20.9% (overlap went from 103,818,926 B to 770,048 B, with 453 GETs in both arms).
- The 28.9% time drop is not. It compares arms that weren't interleaved: cache disabled ran 15:34–15:39, default cache ran 16:10–16:14.
- Throughput rose during the session: 4.95, 5.24 and 5.69 MB/s in disabled runs 1–3; 5.87 MB/s in disabled run 5 at 16:00; 5.71–5.87 MB/s for default cache.
- Against the nearest disabled run (`s3_full-5`, 84.13 s, measured even with nettop running), default cache is 20.5% faster. That matches the byte saving.
- Suggested wording: time fell roughly in proportion to bytes on a bandwidth-bound link; the 94→67 s comparison also includes network drift.

**F2 — The API time is set by the script's own pacing** (`:35-41`, RD `:21`).
- In every run, wall time = 176 × 0.21 s (36.96 s) plus the last request's latency (0.25–0.34 s). This matches 37.218–37.374 s to within 0.13 s.
- The slowest request took 0.81 s, under the 0.84 s at which the 4 connections would have limited throughput.
- So 37.3 s is a chosen constant, not a measure of what the API can do. The S3 full-record times, by contrast, are limited by this host's ~5.8 MB/s link (the single-stream baseline was 3.74 MB/s).
- The API run also returned only 89% of the records, and as JSONL with no Parquet write.
- "Shorter" is literally true, but it compares chosen pacing against link bandwidth. Say so.
