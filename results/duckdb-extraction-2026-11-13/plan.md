# Local anonymous DuckDB extraction spike

Question: can local DuckDB filter OpenAlex 2018 records directly from public S3 and produce Parquet, and what transfer/resource cost does selecting full nested records impose? This is a bounded experimental spike, not a full 2018 export or application feature. User explicitly approved trying the method on this laptop. Query URI stays s3://; transport remains normal S3 HTTPS.

Input is the median-by-size current Works shard, 390189187 bytes and 400000 records. Pin its observed version/ETag and check for changes before and after; fail on mismatch. No authentication: strip AWS environment entries from child processes, point AWS config/credential files and DuckDB persistent-secret directory to empty study-owned files, disable global S3 credential fetching and refresh, use explicit empty S3 config and RequesterPays=false, verify no Authorization credential headers in observable HTTP logs. Do not access any AWS profile, account, metadata endpoint or credential source. Local Parquet output only; no S3 writes.

First witness tiny 64058-byte one-row shard support and logging on the installed DuckDB 2.0.0. Find reliable S3 payload-byte and request metrics before using large source. Prefer exact HTTP Range/Content-Length counters, cross-check known full download size; do not confuse logical read/decompressed bytes, instrumented wall time and network transfer. If only approximate metrics are available, label them and resolve before drawing transfer-ratio conclusions.

Baseline: download the whole fixed shard through unsigned S3 GetObject, count exact bytes and SHA256, record wall/CPU/RSS/disk. Then run local DuckDB COPY for id/year and full-record WHERE publication_year=2018 to create reference outputs. Direct variants run in three fresh processes each, with external-file cache disabled and same memory/thread limits; measure COPY execution wall time, process startup separately, actual S3 payload reads/requests, CPU, peak RSS, DuckDB peak buffer/spill, and Parquet output bytes/rows. Query includes hive_partitioning=false so folder metadata cannot replace raw updated_date values. Verify every output against its local reference using a canonical Arrow value hash/schema/row counts, allowing row-order differences and preserving nested values, duplicates and NULLs. Never substitute count-only metadata for actual extracted rows.

Predeclared transfer targets: id/year <=10% of complete object; full-record extract <=25% for effective selective extraction. A valid result may reject either target. Baseline network download initially one observation, labelled explicitly; independent direct runs=3. No capacity/throughput extrapolation to full corpus. Stop if a case exceeds240s, available disk falls below50GiB, process exceeds8GiB configured database memory, or cumulative observed read payload reaches3GiB; do not expand if full-record variant approaches whole-file transfer. Keep raw source and exported data under ~/work/data, not Git; commit compact evidence/scripts/report and push main per user preference.
